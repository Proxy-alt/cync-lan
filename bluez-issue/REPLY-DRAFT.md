Thanks for the pushback on the first patch — that's a fair objection, and I agree unconditional discovery is the wrong trade for every other device on the bus.

I've written a lazy-verify version instead, and this time I have a full traced repro of it working, on real hardware, against the exact bug this issue describes. Patch attached: `0003-lazy-verify-ccc-v2-verified.patch`.

**What it does.** `discover_descs()` still synthesizes the `0x2902` exactly as it does today. What changes is `register_notify()`: before it ever writes to a handle `discover_descs()` only guessed at, it now issues a single-handle `FIND_INFORMATION` and lets the peer answer for itself. Only if that answer confirms a real `0x2902` does the CCC write happen. If the peer answers with anything else (or doesn't answer), `ccc_handle` is cleared and this reaches the same "no CCC" path `register_notify()` already handles correctly today — so a characteristic whose CCC turns out not to exist gets registered locally with no write at all, same as a device that never claimed to have notify/indicate in the first place. That's one extra round trip, only the first time `register_notify()` is called for a characteristic whose CCC was never actually discovered — a real, discovered CCC is untouched by this patch and costs nothing extra.

**A real bug in the first version, found by actually running it.** `unverified_ccc` (the set of handles `discover_descs()` synthesized) lived on `struct bt_gatt_client`. But `discover_descs()` only ever runs on the *root* client — clones (`bt_gatt_client_clone()`, one per D-Bus consumer, used by `src/gatt-client.c`) share the parent's `gatt_db` rather than discovering it themselves. `register_notify()` is commonly called through one of those clones, whose own copy of `unverified_ccc` is always empty. So the verify step silently never triggered, and the original blind write still happened — the patch compiled clean and looked correct by inspection, but didn't actually change behavior. Fixed with a two-line `root_client()` helper that walks `->parent`, used at both call sites instead of `client->unverified_ccc` directly. I'd have shipped that bug if I'd stopped at "it builds."

**How I actually caught it.** Built and ran this as `bluetoothd` itself (not a harness) on plain Debian, bare metal, no containers — a different machine and a different Bluetooth chipset entirely from my earlier attempts on this issue, specifically to rule out anything about my prior test environment. Connected to a real Cync device (`F4:BC:DA:39:03:D4`), and its notify characteristic's descriptor discovery skipped `0x0013` exactly as this issue describes — `discover_descs_cb()` found `0x0004`/`0x0016`/`0x0019`/`0x001c` as `0x2901` and never queried `0x0013` at all. Calling `StartNotify` on that characteristic with v1 of the patch reproduced the original bug completely unchanged: a `WRITE_REQ` to `0x0013` that timed out 30s later (`src/shared/att.c:timeout_cb() ... 0x12`) and tore down a connection that had been perfectly healthy up to that point. That's what sent me looking for why the "fix" wasn't firing, and turned up the clone bug above.

**With that fixed, identical scenario, immediately after:**

```
verify_ccc_cb() handle 0x0013 confirmed is not a CCC descriptor
```

`StartNotify`'s D-Bus call returns success right away, no write goes out to `0x0013`, and the connection stays up — confirmed via `Device1.Connected` afterward. Same device, same characteristic, same daemon build, same session; only the `root_client()` fix differs between the failing run and the passing one.

I also want to close the loop on where this left off before: my last two attempts here (from a management container, then briefly suspecting a capability/seccomp gap) turned out to be a red herring — connecting to these specific Cync mesh nodes is just genuinely flaky on marginal signal, independent of environment, and this run confirms the actual code path works once a connection holds long enough to reach it.
