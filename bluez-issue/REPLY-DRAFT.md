Following up with v3 — CI on the v2 mirror ([PR #2493](https://github.com/bluez/bluez/pull/2493)) caught real problems, not just style noise, and I want to walk through what actually happened rather than just say "fixed."

**What CI found:** `CheckPatch`/`GitLint` flagged two over-length lines and an over-length title (fixed below). `MakeDistcheck` failed with three test binaries aborting. I didn't have visibility into which tests or why from the CI summary, so I reproduced it locally — built both an unpatched baseline and the patched tree from the same commit, ran `make distcheck` on both. Baseline: 41/41 unit tests pass. Patched: 38/41 — `test-micp`, `test-mcp`, `test-bap` all abort. That's a real regression this patch introduced, not flakiness.

**Tracing it down, in `unit/test-micp`, found two real bugs in v2:**

1. `unverified_ccc` lived on `struct bt_gatt_client`, but `discover_descs()` only ever runs on the *root* client — `register_notify()` is commonly called through a *clone* (`bt_gatt_client_clone()`, used by `src/gatt-client.c` per D-Bus consumer, and by profile implementations like `bt_micp`), whose own copy of that queue is always empty. The verify step silently never fired. `unit/test-micp` reproduced the *original* bug exactly, unchanged, with v2 applied: a `WRITE_REQ` to the synthesized handle that got no response — which in a real session is the 30s ATT timeout and teardown this issue is about. Fixed with `root_client()`, a two-line walk up `->parent`.

2. Fixing that surfaced two more, together: the CCC write could get skipped, and a *later* application write could go out on the wire ahead of it. Root cause: `bt_gatt_discover_descriptors()` (what the verify step uses) isn't tracked in `client->pending_requests` the way `bt_gatt_client_write_value()`/read are. `notify_client_idle()` only watches `pending_requests`, so it considered the client idle — and fired every registered idle callback, letting application code run — while the verify `FIND_INFORMATION` was still genuinely outstanding on the wire. Separately, `resume_after_ccc_verify()` reused `register_notify()`'s own "`notify_count > 1` means someone already wrote it" check, which stops being true once there's an async gap: other callers can (correctly) queue up behind `ccc_verify_req` and bump `notify_count` before verification even resolves.

Also found and fixed a real leak (3 `struct bt_gatt_result` plus their backing allocations, confirmed via LeakSanitizer): `verify_ccc_cb()` never released the reference `bt_gatt_discover_descriptors()` returns — every other discovery completion in this file does (see `discovery_req_clear()`).

**Patch 1/2** ([0004](./0004-lazy-verify-ccc-v3-1of2.patch)) has the actual fix, all of the above. **Patch 2/2** ([0005](./0005-test-micp-find-info-2of2.patch)) updates `unit/test-micp`'s three affected subtests to expect the new exchange.

**Verified:** `./unit/test-micp` — 7/7 pass, zero leaks under LeakSanitizer, on the exact commit CI tested against (`4b92dddc`). Both patches apply clean via `git am` to a fresh clone of current master.

**Not done yet, and I think it's worth discussing rather than just patching around:** `unit/test-mcp` and `unit/test-bap` still fail (`MCP/CL/CGGIT/CHA/BV-04-C`, `BAP/UCL/DISC/BV-03-C`), and tracing `test-mcp` down turned up something more interesting than a missing mock entry.

MICP registers one characteristic's notify at a time (idle-gated between them), so the fix from patch 1/2 is enough — the write always ends up correctly ordered relative to whatever the application does next. MCP's `foreach_mcs_char()` doesn't work that way: it walks every characteristic in one synchronous pass, calling `read_value()`/`register_notify()` for each as it goes. In the original code that was fine, since `register_notify()`'s CCC write went out synchronously, in loop order. With the verify step, a synthesized characteristic's write is now *deferred* behind an async round trip - and by the time it resolves, the loop has already moved on and queued the *next* characteristic's read ahead of it in `bt_att`. So for `TRACK_CHANGED` specifically: the `FIND_INFORMATION` goes out and gets answered correctly, but then `TRACK_TITLE`'s read (queued earlier, in loop order) goes out before my resulting CCC write does. Confirmed at the byte level - traced the exact wire sequence, no guessing.

Nothing is lost or corrupted - the write still happens, just reordered relative to unrelated traffic, which is harmless in practice. But it means `test-mcp`'s mock script can't be fixed with a single `FIND_INFORMATION` insertion like MICP's could; it needs the whole synthesized-CCC write relocated to wherever the rest of that same loop's traffic actually lands, which depends on how many other characteristics come after it. I didn't want to guess at that and ship an unverified reorder, so I'm flagging the actual behavior instead: **any caller that batches multiple `register_notify()` calls in one synchronous pass, for a characteristic whose CCC needs verifying, will see that specific write reordered after whatever else that same pass already queued.** Worth knowing whether that's acceptable as designed, or whether it points at a different fix than a plain per-characteristic async gate.

**Checked `test-bap` too, and it's the identical pattern - which actually pins down exactly when this shows up.** BAP's `DISC_SNK_ASE` scripts two ASEs, each with its own read-then-CCC-write. The single-ASE cases (`DISC_SRC_ASE_LC3`, `DISC_SNK_ASE_NO_LOCATION`) needed nothing more than the same single `FIND_INFORMATION` insertion MICP needed, and passed clean. The moment a test has *two* ASEs discovered in the same `gatt_db_service_foreach_char()` pass, it hits the same reordering MCP did: the first ASE's `FIND_INFORMATION` goes out and gets answered, then the *second* ASE's read (`SNK_HND(1)`, queued earlier in the same loop) goes out before the first ASE's resulting CCC write does. Byte-for-byte the same shape as the MCP trace.

So the actual rule, now confirmed on two independent profile implementations: **the reordering only happens when a caller registers notify for more than one characteristic inside the same synchronous `gatt_db_service_foreach_char()` pass.** MICP never hits it because MICS has exactly one relevant characteristic per service, so there's never a "next" registration in the same pass to race ahead. MCS (11 characteristics) and ASCS (multiple ASEs) both do. This isn't a per-profile quirk I'd need to chase file by file - it's one general property of the design, and I'd rather raise it as that than keep sending individually-reverse-engineered test fixes.

I haven't touched `unit/test-mcp.c`/`unit/test-bap.c` - reverted the exploratory edits on both once I had the trace, so there's nothing incomplete or guessed-at sitting in the patch set. Happy to take direction on whether this needs a different fix shape (something that holds a per-caller "batch" open until all the synthesized-CCC writes in it resolve, maybe) or whether reordering unrelated ATT traffic behind a verify is fine to accept as-is and it's just these two tests' mocks that need updating for real use elsewhere.
