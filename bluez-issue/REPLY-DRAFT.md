Following up with v3 — CI on the v2 mirror ([PR #2493](https://github.com/bluez/bluez/pull/2493)) caught real problems, not just style noise, and I want to walk through what actually happened rather than just say "fixed."

**What CI found:** `CheckPatch`/`GitLint` flagged two over-length lines and an over-length title (fixed below). `MakeDistcheck` failed with three test binaries aborting. I didn't have visibility into which tests or why from the CI summary, so I reproduced it locally — built both an unpatched baseline and the patched tree from the same commit, ran `make distcheck` on both. Baseline: 41/41 unit tests pass. Patched: 38/41 — `test-micp`, `test-mcp`, `test-bap` all abort. That's a real regression this patch introduced, not flakiness.

**Tracing it down, in `unit/test-micp`, found two real bugs in v2:**

1. `unverified_ccc` lived on `struct bt_gatt_client`, but `discover_descs()` only ever runs on the *root* client — `register_notify()` is commonly called through a *clone* (`bt_gatt_client_clone()`, used by `src/gatt-client.c` per D-Bus consumer, and by profile implementations like `bt_micp`), whose own copy of that queue is always empty. The verify step silently never fired. `unit/test-micp` reproduced the *original* bug exactly, unchanged, with v2 applied: a `WRITE_REQ` to the synthesized handle that got no response — which in a real session is the 30s ATT timeout and teardown this issue is about. Fixed with `root_client()`, a two-line walk up `->parent`.

2. Fixing that surfaced two more, together: the CCC write could get skipped, and a *later* application write could go out on the wire ahead of it. Root cause: `bt_gatt_discover_descriptors()` (what the verify step uses) isn't tracked in `client->pending_requests` the way `bt_gatt_client_write_value()`/read are. `notify_client_idle()` only watches `pending_requests`, so it considered the client idle — and fired every registered idle callback, letting application code run — while the verify `FIND_INFORMATION` was still genuinely outstanding on the wire. Separately, `resume_after_ccc_verify()` reused `register_notify()`'s own "`notify_count > 1` means someone already wrote it" check, which stops being true once there's an async gap: other callers can (correctly) queue up behind `ccc_verify_req` and bump `notify_count` before verification even resolves.

Also found and fixed a real leak (3 `struct bt_gatt_result` plus their backing allocations, confirmed via LeakSanitizer): `verify_ccc_cb()` never released the reference `bt_gatt_discover_descriptors()` returns — every other discovery completion in this file does (see `discovery_req_clear()`).

**Patch 1/2** ([0004](./0004-lazy-verify-ccc-v3-1of2.patch)) has the actual fix, all of the above. **Patch 2/2** ([0005](./0005-test-micp-find-info-2of2.patch)) updates `unit/test-micp`'s three affected subtests to expect the new exchange.

**Verified:** `./unit/test-micp` — 7/7 pass, zero leaks under LeakSanitizer, on the exact commit CI tested against (`4b92dddc`). Both patches apply clean via `git am` to a fresh clone of current master.

**Not done yet:** `unit/test-mcp` and `unit/test-bap` hit the identical class of gap — their own CCC-enable sequences need the same `FIND_INFORMATION` step added. I traced `test-mcp`'s far enough to confirm it's the same root cause (register_notify() firing correctly, mock script just not accounting for the new exchange yet), but the exact insertion points depend on that profile's own attach/discovery ordering, which I haven't fully mapped yet — didn't want to guess and ship something unverified. Flagging plainly rather than claiming both are done when only one is.
